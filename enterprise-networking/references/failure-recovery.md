# Failure drills and scoped recovery

Rehearse in an isolated owner-controlled environment before a production cutover. Bind every trigger to a measured threshold and observation window selected for the actual application; the fixture's 1/3-second BGP timers and 35-second polling budget are lab values, not production defaults. Do not interrupt a real peer/tunnel just to complete a checklist.

| Failure | Diagnose and contain | Recovery evidence |
|---|---|---|
| WireGuard tunnel loss | Compare fresh application probes, transfer/handshake changes, exact endpoint reachability, AllowedIPs, interface state and route selection on both sides. A silent idle peer need not have a fresh handshake. Freeze further stages; preserve the management/OOB path. | Restore the exact owned interface/peer/route state if authorized and safe. Require fresh encrypted bidirectional traffic, renewed BGP adjacency/withdrawal recovery and absence of unexpected routes through the full hold window. |
| Prefix leak/default/over-specific | Stop propagation; identify originating peer, AFI, attached inbound/outbound filter and affected downstream peers. Coordinate containment at the narrowest supported policy boundary with remote owners. Preserve received/accepted/advertised inventories before clearing state. | Reapply the reviewed exact-prefix filter. Use a supported soft refresh when safe; hard reset has separate impact. Observe withdrawal everywhere affected, intended routes retained, kernel next hops reconciled and application/segmentation checks passing. |
| Wrong ACL order or policy | Compare full family/hook/priority/ordered rules and fresh-flow counter deltas; check concurrent automation and other base chains. Avoid a global allow or global ruleset flush. | Restore only the exact owned table/chain/rule slice from a tested before-state; use a checked atomic nft transaction. Prove intended allow and deny paths and unchanged unrelated tables. |
| Asymmetric/MTU regression | Attribute failed direction and size using contextual route lookups, validation/filter counters and bounded data-plane tests. Preserve evidence before changing routes or MTU. | Restore the exact route/rule/MTU state chosen in the recovery plan, then repeat bidirectional and size-dependent acceptance. A working small ping does not close the incident. |

## Concrete staged recovery

The exact plan must name the owner, target/namespace/VRF, peer, prefixes, allowed/denied flows, expected before/intended digests, convergence deadline, rollback authority and independent management path. Reconcile the remote side's actual state rather than a ticket assertion. Capture persistent and active config ownership; kernel route or `wg set` reversal alone may be overwritten by automation or disappear at reboot.

Prepare separately reviewed candidate and rollback artifacts. For nftables, use `nft --check -f` against the confirmed namespace, then one atomic `nft -f` transaction scoped to the owned table/slice; never `flush ruleset` on a shared host. Snapshot evidence containing comments is not a ready-to-execute rollback script. For FRR, restore the exact policy sequence and attachment through the owning configuration system, reconcile running/persistent config and inspect actual accepted/advertised withdrawals. For WireGuard, avoid replaying `wg-quick` hooks or `SaveConfig` behavior without reviewing their side effects and configuration owner.

After a partial failure, inventory what changed at every peer/site before retrying. Unchanged command argv does not prove referenced config is unchanged. If a concurrent edit changed the old revision, re-plan recovery instead of overwriting it. If restoring the previous route/ACL would spread a leak, expose a protected segment, resurrect a compromised peer/key or destroy the remaining management path, stabilize through an explicitly owned containment plan and report the missing authority/capability. Never fabricate recovery success because an inverse command exited zero.

Report actual changed devices/peers/prefixes/rules, observation times, raw/diff artifact digests, fresh application and negative-flow evidence, convergence and recovery result. Use `partially_verified` if any remote side, propagation boundary or application check remains unknown; `rolled_back` requires observed recovery. Local matching snapshots cannot authenticate target state or a human approval.

## Executable repository rehearsal

`tests/smoke_enterprise_networking.py` creates only randomly named network namespaces and their veth/WireGuard interfaces, two private bgpd processes and nft tables in those namespaces. Root/CAP_NET_ADMIN and kernel support are mandatory; unavailable tools/capabilities fail the workflow. Secrets are generated at runtime in a private temporary directory, never printed, committed or uploaded. Cleanup terminates only captured child processes, deletes only namespaces successfully created by this invocation and removes its private temporary directory. It does not query or modify a production target.

The test checks actual encrypted bidirectional ICMP, a real WireGuard handshake, inner MTU boundary, first-match nft allow/deny ordering and counters, preservation of an unrelated sentinel table, strict-rp_filter asymmetric-route failure and exact route recovery, real FRR accepted-prefix leak injection/detection/filter rollback, and tunnel loss followed by BGP route withdrawal/reconvergence and encrypted traffic recovery. Standalone bgpd deliberately excludes zebra/kernel installation; static kernel routes are verified independently. This is a repeatable lab recovery scenario, not HA/failover or production RTO certification.

Official baseline: [FRR import/export and soft refresh](https://docs.frrouting.org/en/stable-8.4/bgp.html), [nft atomic replacement](https://wiki.nftables.org/wiki-nftables/index.php/Atomic_rule_replacement), [WireGuard CLI](https://www.wireguard.com/quickstart/). Refresh relevant version-specific pages before change.
